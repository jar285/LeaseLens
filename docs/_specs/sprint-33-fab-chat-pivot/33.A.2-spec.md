# Sprint 33.A.2 — Chat drift insurance (ScanTimeline gate + deterministic receipt)

> Draft by the agent from the approved plan, for the user's **Spec-QA** review/push-back gate
> (methodology §2) before any TDD. Resolves the deferred carries **A3 + A4** from
> [`33.A-and-33.B-spec.md`](33.A-and-33.B-spec.md). Single-purpose slice.

## Context

Sprint 33.A retired the chat's redundant scan-summary surface **at the model level only**: the system
prompt forbids the model from reprinting findings as a table and reduces the auto-scan turn to a single
short ack. Sprint 33.B gave the right pane the canonical verdict (`computeScanVerdict`) + ungraded line.
Two client-side carries were explicitly **deferred** as polish (no current contradiction, only
redundancy) — they are this slice:

- **A3.** `ScanTimeline` still renders *inside* the auto-scan chat turn, duplicating the right-pane
  staircase. Two progress timelines for one scan force the user to decode which is authoritative — a
  **Steve Krug / Dieter Rams** redundancy ("less, but better"). Not contradictory post-33.A, just noise.
- **A4.** The chat's "scan complete" signal still rides on the model's prose plus a fragile 2020-era
  length heuristic. The number/wording the user reads in chat should be *computed from the same
  gradings the cards render* — a **Source-Grounded AI** invariant — not the model's freeform text.

### The drift vector (verified against current code, not assumed)

After 33.A the model writes a short ack. The 33.A spec's own example — *"Done — see the findings on the
right; ask me about any clause."* — is ~60 chars, **below** `SUBSTANTIVE_REPLY_MIN_CHARS = 80`
([ChatTranscript.tsx:56](../../../src/components/chat/ChatTranscript.tsx#L56)). So
`modelProducedClosingReply()` returns `false`, and the **verbose** `scan-narrative` summary
("I finished scanning your lease. I found N red flags: H high, M medium, L low…") still appends in the
transcript ([ChatTranscript.tsx:130-134](../../../src/components/chat/ChatTranscript.tsx#L130-L134)).

That heuristic is Sprint 20 debt: built when the model *either* wrote a full findings list (≥80 →
suppress synthetic) *or* fell silent (<80 → show the synthetic safety net). 33.A made the model's ack
land squarely in the "show the verbose tally" branch — **Martin Fowler / Ward Cunningham** debt that the
trim made obsolete. The verbose synthetic now re-states a finding tally in chat, exactly the surface
33.A meant to remove.

**Consistency win:** the 33.A system prompt already tells the model *"the client UI shows a deterministic
'Scan complete — N findings on the right' line"* ([system-prompt.ts ~166](../../../src/lib/chat/system-prompt.ts)).
That line does **not** exist yet. A4 makes the implementation honour the contract the prompt already
depends on (**Arnaud Lauret**: don't promise a surface you don't ship).

### A3 — gate ScanTimeline off the auto-scan turn (Tenant only)

Target: [ChatMessage.tsx:287-338](../../../src/components/chat/ChatMessage.tsx#L287-L338) (`ToolInvocationsBlock`)
and [ChatUI.tsx:694](../../../src/components/chat/ChatUI.tsx#L694) (the only live `ChatTranscript`
consumer).

1. Add optional `isAutoScanTurn?: boolean` to `ChatMessageProps`
   ([ChatMessage.tsx:48-64](../../../src/components/chat/ChatMessage.tsx#L48-L64)).
2. Change the gate from
   `const showTimeline = viewerRole === 'Tenant' && scanInvocations.length > 0;`
   to additionally require `&& !isAutoScanTurn`.
3. When gated off for a **Tenant** auto-scan turn, render **neither** the `ScanTimeline` **nor** the
   scan-tool-card fallback. The current `else` branch dumps raw `ToolCard`s
   ([ChatMessage.tsx:308-312](../../../src/components/chat/ChatMessage.tsx#L308-L312)) — leaking
   developer trace into the tenant view would be *worse* than the timeline. `nonScanInvocations`
   (e.g. `draft_negotiation_email` → `NegotiationEmailCard`) **still render** unchanged.
4. **Reviewers/Admins are unaffected** (`isAutoScanTurn` only suppresses the Tenant timeline path).
5. Compute `isAutoScanTurn` in **ChatUI**, which holds both `activeConversationId` and
   `autoScanConversationId` ([ChatUI.tsx:251-255](../../../src/components/chat/ChatUI.tsx#L251-L255)):
   when `activeConversationId === autoScanConversationId`, mark the **first** assistant message bearing
   scan invocations (`extract_clauses` / `grade_clause_severity`). The flag survives
   `ChatTranscript.mergeSyntheticMessages` (`merged.push(...real)` preserves message fields) and the
   `<ChatMessage {...msg} />` spread — no new threading prop needed.
6. A later **user-initiated "scan again"** is a *non-first* scan turn → `isAutoScanTurn` is false → it
   **keeps** its `ScanTimeline`. This is the load-bearing distinction (auto-scan turn only).

### A4 — replace the verbose summary with a deterministic minimal receipt

Reuse the existing trailing synthetic-summary slot in
[scan-narrative.ts](../../../src/components/lease/scan-narrative.ts) (already deterministic, derived
from `toolEvents`, stable id `synthetic:scan-complete:{lease_id}:{extractIndex}` → idempotent
merge-by-id). Do **not** add new state.

1. Replace `buildSummary`'s `scan-complete` + `scan-partial` copy with the minimal receipt:

   ```
   Scan complete. {N} findings on the right — ask me about any of them.
   ```

   **N is pinned by D1** (below) — it must equal the red-flag card count the user can verify on the
   right pane, NOT the "attempted" count from the original A4 text. Keep the stable id and the
   follow-up chips (`SCAN_COMPLETE_PROMPTS`).
2. **Retire** `SUBSTANTIVE_REPLY_MIN_CHARS` / `modelProducedClosingReply`
   ([ChatTranscript.tsx:49-62, 130-134](../../../src/components/chat/ChatTranscript.tsx#L49-L62)). The
   receipt is now minimal and complementary to the ack, so it renders once the scan completes
   regardless of ack length. **Keep** the `isStreaming` guard (no mid-stream flicker).
3. **No `ChatStreamContext` flag.** The 33.A spec's risk note suggested a
   `scanCompleteReceiptShownForConversation` flag to prevent double-fire; the stable-id +
   merge-by-id pattern *already* guarantees once-only rendering. Adding mutable state would be
   redundant and would stress the pinned chat/parser boundary. **Dan Abramov**: derive, don't store.
4. **Fatal case kept distinct (D2).** When ≥50% of grade attempts errored (`scan-fatal`), the right
   pane's verdict is empty/idle and the user needs an in-chat recovery path. Keep a minimal fatal
   receipt + its `SCAN_FATAL_PROMPTS` ("Try again"). Only `complete`/`partial` collapse to the receipt
   above (the right pane's ungraded line owns the "some couldn't be graded" nuance per 33.B3).

### Decisions locked in this draft (open to QA push-back)

- **D1 — receipt N (drift-critical).** N = **red-flag card count = high + medium + low**, i.e. the
  existing `tally.total` in `scan-narrative.ts`. This equals the red-flag cards the user counts on the
  right (the count strip's high/med/low; the lone OK card is not a "finding"; ungraded clauses have no
  card and live on the separate ungraded line). The original A4 text ("valid + errored = all attempted")
  would put a number in chat that has no matching object on the right — a *new* drift in a
  drift-insurance slice. We pin a Kent-C-Dodds test: **receipt N === number of `red-flag-card`
  testids**. *(Note: `computeScanVerdict`'s headline "N findings" is top-tier-only and can differ in
  multi-tier leases — see Spec-QA; that is a 33.B framing question, out of scope here.)*
- **D2 — collapse complete+partial, keep fatal.** As in A4.4.
- **D3 — Tenant auto-scan suppresses both timeline and tool-card fallback; reviewers unchanged.** As in A3.3-4.
- **D4 — retire the `<80` heuristic.** It is the drift vector; the deterministic receipt replaces its job.
- **D5 — keep the Sprint 29.11 transient banner.** ([ChatUI.tsx:673-693](../../../src/components/chat/ChatUI.tsx#L673-L693))
  It is an ephemeral dismissable nudge with no count; the receipt is the persistent counted anchor.
  Mild redundancy accepted; any merge is separate polish.

## Spec QA — gaps, risks, drift

- **Receipt-vs-verdict count mismatch in multi-tier leases.** `computeScanVerdict`'s headline counts the
  **top tier only** ("High risk — 3 findings…" when 3 high + 5 medium), while the receipt (D1) counts
  **all** red flags (8). Both are deterministic and neither contradicts the cards, but a careful user
  could read "3" and "8" on two surfaces. On the sample lease they coincide (13/13), masking it.
  *Question for QA:* is the receipt's "all red flags" count the right one, or should the chat carry
  **no number** at all ("Scan complete — your findings are on the right; ask me about any of them.") —
  zero numeric drift, but needs a one-line system-prompt tweak to drop "N"? Recommend keeping the count
  (honours the prompt contract); flagging the no-count alternative as the maximally-conservative option.
- **"First scan-bearing assistant message" identification.** If the server ever replays the auto-scan
  conversation such that a non-first assistant message carries the scan invocations, the gate could
  mis-target. Mitigation: identify by *first* scan-bearing assistant message within the conversation,
  and pin both paths with tests. Exact mechanism chosen during TDD (the 33.A spec left this open).
- **Empty `ToolInvocationsBlock` div.** When every invocation on the gated turn is a scan invocation,
  the block renders an empty `<div className="my-2">`. Harmless; tests assert absence of timeline/cards,
  not absence of the wrapper. Tidy only if trivial.
- **Fatal receipt copy.** Keeping a distinct fatal variant means `scan-narrative` retains three states;
  only the copy of two changes. Confirm the fatal copy + "Try again" chips still read well next to the
  right pane's (empty) verdict.
- **Test blast radius.** `scan-narrative.test.ts` currently pins the verbose complete/partial copy —
  those assertions get rewritten (TDD red→green). No behaviour outside the transcript receipt changes.
