# Sprint 33.0 — Implementation Notes & QA Report

## What was completed

The chat route accepts a new optional `startNewConversation: boolean` field on the POST body. When `true`, the route IGNORES any `conversationId` supplied in the body and ALWAYS creates a fresh conversation row. `AutoScanRunner` sets the flag on every auto-scan POST.

This pins the **"one conversation per lease scan"** domain invariant at the server boundary. Prior-lease tool blocks can no longer leak into a freshly-uploaded lease's context window — even if the client sends a stale `conversationId` inherited from SSR.

The change is small (3 lines in route.ts, 1 line in AutoScanRunner.tsx, schema addition) and entirely additive: existing FAB chat flows that omit the flag continue to reuse the active conversation normally.

## Live Playwright re-verify (Kent-C-Dodds invariant in the live system)

Repro: clean DB state via dev-server restart, then through the live UI:

1. Click Replace → drop `sample-nj-clean-lease.pdf` (lease A).
2. Wait ~35 seconds for the auto-scan to complete.
3. Click Replace → drop `sample-nj-residential-lease.pdf` (lease B).
4. Capture the AutoScanRunner POST bodies AND the streamed `conversationId` envelopes via a fetch tee.

Observed bodies (both POSTs):

```json
{
  "message": "Run the standard scan on my active lease …",
  "conversationId": "8a8d7cf2-bd97-4e1b-bb8e-a3a4d1b5d2ba",  // ← STALE, from SSR
  "startNewConversation": true,                                // ← NEW
  "forceScan": true                                            // ← from Sprint 32.1
}
```

Observed `conversationId` envelopes returned by the server:

| Upload | Returned conversationId |
|---|---|
| Lease A | `df857f94-a842-4b8f-a358-2ca53e389b69` |
| Lease B | `bc0bc0d7-2ac4-413e-b20e-121a0fd8ca25` |

**Two distinct fresh UUIDs, neither equal to the stale `8a8d7cf2-…` the client sent.** The flag is doing exactly what the Kent-C-Dodds invariant required: the server treats every fresh scan as a brand-new conversation, regardless of stale SSR-bound state on the client.

## Drift observed

None.

The `WorkspaceRouterShell` conversationId state ownership refactor that the brainstorm Appendix proposed turned out **not to be needed** — the server-side flag is sufficient. The stale SSR-bound `conversationId` is still sent in the body, but the server ignores it under the flag. Simpler than refactoring client-side state ownership, equally correct, and tested.
