# Sprint 33.0 — Conversation Scoping (Foundation)

## Context

Sprint 32.1's `forceScan + tool_choice: any` guarantees the model calls tools. But Sprint 32.2.0's diagnostic surfaced a deeper invariant gap: the `conversation_id` is being reused across fresh uploads, so prior-lease tool blocks remain in the model's context window. Even after Sprint 33.A trims the chat surface, the chat's *Q&A* would still occasionally answer from prior-lease context.

The bug class is a Dan Abramov / Eric Evans modeling mismatch: `conversation_id` is implemented as a durable per-workspace session, but the domain reality is **one conversation per lease scan**. Replace lease → new conversation.

## Spec

### Invariants (carried)

- Within a single scan, prior tool_result blocks remain in context for follow-up Q&A (Sprint 23e contract preserved).
- Manual user-typed chat messages continue using the current `conversationId` — no regression on normal multi-turn FAB conversations.
- `forceScan: true` from Sprint 32.1 stays. Adding `startNewConversation: true` as a separate, composable flag.
- `chatRequestBodySchema` change is purely additive — one new optional field.
- The existing "conversationId from a foreign workspace falls through to a fresh conversation" semantics ([route.ts:284-307](../../../src/app/api/chat/route.ts#L284-L307)) is unchanged.

### New behaviour

**A.** [route.ts:36-46](../../../src/app/api/chat/route.ts#L36-L46) accepts a new optional field:

```ts
startNewConversation: z.boolean().optional(),
```

**B.** When `startNewConversation === true`, the conversation-resolution branch [route.ts:286-307](../../../src/app/api/chat/route.ts#L286-L307) IGNORES any `conversationId` in the body and ALWAYS creates a fresh conversation row. The existing `let activeConversationId = conversationId ?? null;` line becomes:

```ts
let activeConversationId =
  startNewConversation === true ? null : (conversationId ?? null);
```

The downstream lookup-or-create logic at lines 288-307 is unchanged — passing null reliably triggers the "create new" branch.

**C.** [AutoScanRunner.tsx:122-130](../../../src/components/lease/AutoScanRunner.tsx#L122-L130) sends `startNewConversation: true` in its POST body. AutoScanRunner is the canonical "new lease started" signal — when it fires, the prior conversation should never carry over.

### Definition of done

- Schema accepts the new field.
- Route forces fresh conversation when the flag is true, regardless of `conversationId` in the body.
- AutoScanRunner sends the flag.
- Tests pin the contract (red→green).
- `npm run lint` / `typecheck` / `npm test` / `npm run build` all green.
- Live re-verify: upload lease A → ask Q in FAB → upload lease B → ask same Q → confirm lease A's findings don't bleed into lease B's answer.

## Spec QA — gaps & risks

- **Risk: regressing user-typed FAB chat continuity.** Mitigation: AutoScanRunner is the ONLY caller setting the flag (verified via grep before commit). User-typed messages send the current conversationId without the flag — server reuses the conversation normally.
- **Risk: Sprint 23e "REUSE prior tool_results" contract.** Mitigation: the boundary is per-lease-scan, not per-message. Within a single conversation (= single scan), prior tool blocks ARE still reused. Sprint 23e tests don't reference fresh-upload semantics.
- **Risk: the SSR-loaded `props.conversationId` in `WorkspaceRouterShell`.** AutoScanRunner currently inherits this prop. After 33.0, the server creates a new conversation anyway when the flag is set; the server's response stream emits the new `conversation_id` envelope; the client's `ChatStreamContext.autoScanConversationId` adopts it. Existing wiring (Sprint 26c.10) handles this transparently — no WorkspaceRouterShell change required.
- **Risk: stale prior-session conversation_id surviving cookie wipes.** If the dev SQLite DB has older conversations for the same user/workspace, the recent-conversation cookie binding in the client could surface them. The flag short-circuits that path at the server boundary.

## Out of scope

- Sprint 33.A (chat trim) and 33.B (right-pane verdict) — co-dependent slice, ships after 33.0 lands and is verified.
- The `WorkspaceRouterShell` conversationId state ownership refactor proposed in the brainstorm Appendix — not needed if the route honors the flag (simpler).
